# v0.4.9 PRD:首页拆分 + 桌面图标 + 导航重构

> 日期:2026-07-22 ~ 2026-07-23
> 上一版:v0.4.8(见 `docs/v0.4.8/`)
> 性质:UI / 资产重构(无新数据模型,无新 API 端点)

## 0. 文档定位

本 PRD 事后补写,记录 v0.4.9 三件事的**设计动机与决策**:
1. 首页 `/` 从「阅读仪表盘」拆为「个人工作台」,原内容搬到 `/kb`
2. 为 `start_kb.vbs` 桌面启动配置专属多尺寸图标
3. 主导航精简,文章入口收进知识库子导航

325 passed(无新增测试 —— 纯 UI 与静态资产)。

## 1. 动机:为什么要拆首页

v0.4.8 之前,首页 `/` 同时承担两个职责:
- **阅读管理仪表盘**:未读 / 已读 / 稍后读卡片 + 阅读进度统计
- **知识库入口**:所有功能的导航起点

随着 v0.4.8 事件系统、以及规划中的任务系统加入,首页信息密度过高,定位模糊。
用户打开应用,既想看「今天有什么要做的」,又想看「最近读了什么」,两套心智模型打架。

**决策**:拆成两个页面,各司其职。

| 页面 | 路由 | 定位 | 核心问题 |
|---|---|---|---|
| 工作台 | `/` | 个人驾驶舱 | 「今天我要做什么 / 看什么」 |
| 知识库 | `/kb` | 文章阅读管理 | 「我的文章库现在什么状态」 |

工作台聚焦**主动产出**(任务 / 时间线 / 即将截止),知识库聚焦**被动消费**(阅读 / 收藏 / 稍后读)。

## 2. 路由设计

```
GET /    → workspace.html       (工作台)
GET /kb  → knowledge_base.html  (知识库,原首页全量搬迁)
```

**为什么不保留 `/` 作为仪表盘、新建 `/workspace`**:
- 工作台是更高频的入口(每天打开看任务),应该是默认页
- 知识库是低频查阅(偶尔进去看统计),放二级路由合理
- 符合「主动产出优先于被动消费」的产品重心

**数据端点不变**:`/api/dashboard`、`/api/dashboard_full`、`/api/recent` 等仍由 `dashboard.py` 提供,
两个页面只是不同的前端消费组合。工作台多消费了任务/事件相关端点(在 v0.4.10 任务系统落地后才有意义)。

## 3. 工作台布局决策

三栏布局(`ws-layout` grid `minmax(0,1fr) 320px`):
- **主列 `ws-main`**:今日时间线(横向 5 节点)+ 当前任务(视觉中心)+ 底部辅助卡片
- **右侧 `ws-rail`**:推荐阅读 + 最近阅读(sticky 定位,跟随滚动)

**为什么时间线放最上**:时间线回答「接下来有什么事」,是打开工作台的第一诉求。
**为什么当前任务卡是视觉中心**:任务系统(v0.4.10)是本阶段主线功能,工作台为它服务。
**为什么推荐阅读在右侧而非主列**:阅读是被动消费,不抢主列注意力,但 sticky 保证随时可见。

## 4. 桌面图标决策

**为什么用 `.ico` 而非 `.png`**:Windows 快捷方式(`.lnk`)的 `IconLocation` 原生支持 `.ico`,
且 `.ico` 可内嵌多尺寸,系统按显示场景(DPI / 任务栏 / 文件资源管理器)自动选最佳尺寸。

**为什么做 6 尺寸**:16(任务栏)/ 32(普通)/ 48(桌面)/ 64 / 128 / 256(高 DPI 资源管理器大图标),
覆盖 Windows 所有显示场景。

**白底修复为什么不直接重新生成**:原图主体设计已定,重做成本高;flood-fill 抠除连通白底保留主体,
是性价比最高的修复。约 31% 像素转透明,边缘主体完整保留。

## 5. 导航精简决策

**为什么文章入口收进子导航**:搜索 / 全部文章 / 投稿 / 最近阅读 逻辑上都属于「知识库」子域,
平铺在主导航稀释了核心入口(工作台 / 知识库 / 收藏夹 / 日历)。

**实现**:`/kb` 顶部加 `.kb-subnav`(知识库子导航),主导航删 4 项(11 → 7)。
访问文章子页时「知识库」一级入口保持高亮(active_nav 聚合判断)。
